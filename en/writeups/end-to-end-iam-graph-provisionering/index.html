End-to-End IAM, Part 2: Provisioning to Entra ID with Microsoft Graph

By Andreas Krisby 2026-07-26 5 min read

This is part 2 of the series on end-to-end-iam. Part 1 covered why Elytra and Ascendra are fully separate systems, and how an event log (an outbox) keeps them in sync. This part covers what happens once Ascendra knows an employment record has changed: how it actually creates, updates, and disables real user accounts in Entra ID.

First attempt: SCIM was the wrong path

SCIM (System for Cross-domain Identity Management) is a well-established standard for provisioning users between systems, and my first instinct was to use it. That turned out to be the wrong path for this scenario.

SCIM works by having the target system expose an inbound endpoint that an external party provisions against. Entra ID does the exact opposite here: Entra ID is the target directory. There’s no inbound SCIM endpoint in Entra ID to send users to. SCIM is instead used by Entra ID in the other direction, when Entra itself provisions users onward to other SaaS services (for example, a third-party app that gets its accounts created by Entra).

Since Ascendra needs to write into Entra ID, not receive data from it, SCIM was never the right tool here.

The right path: Microsoft Graph

Microsoft Graph is Microsoft’s API for Entra ID and the rest of Microsoft 365. It’s an interface other programs talk to in order to read and change data — for example, to create a user, update their attributes, or disable an account. Each such request is a Graph call.

Ascendra authenticates with Microsoft Graph using the Client Credentials flow, an OAuth 2.0 flow built for programs talking to each other without a human logging in. In short:

  1. Ascendra sends its client ID and client secret (a secret key) to Entra ID’s token endpoint.
  2. Entra ID responds with an access token, valid for a limited time.
  3. Ascendra attaches that token to every subsequent Graph call, until it needs to be renewed.

There’s never a signed-in person in this flow. The permissions belong to the app itself, not to a user — this is called application permissions, as opposed to delegated permissions, which inherit the rights of whoever is signed in.

The app registration in Entra ID

To make this work, I had to register Ascendra as an app in Entra ID, with a specific set of settings:

  • Single Tenant: the app can only be used against our own Entra ID tenant, not by other organizations. There’s no reason to make it multi-tenant here.
  • No Redirect URI: a Redirect URI is only needed for interactive sign-in. Since the Client Credentials flow never involves a login screen, none is needed.
  • User.ReadWrite.All: permission to read and write every user account in the tenant. This is the permission that actually makes provisioning possible.
  • Organization.Read.All: permission to read organization info, such as which domains are verified in the tenant (more on why below).
  • Admin Consent: since these are powerful, tenant-wide permissions, an administrator has to explicitly approve them before the app can use them. There’s no sneaking this kind of permission through.
  • Client Secret: the secret key Ascendra uses to prove its identity in step 1 above.

This combination is deliberately narrow. Ascendra gets exactly the scope it needs to manage user accounts, no more and no less.

What Ascendra actually sends

When an event comes in from the outbox (see part 1), Ascendra translates it into concrete Graph calls:

  • employee.created → a new user object is created in Entra ID with the correct name, department, and account status.
  • employee.updated → existing attributes on the user are updated.
  • employee.activated → the account is set to active (accountEnabled = true).
  • employee.terminated → the account is disabled (accountEnabled = false).

That sounds straightforward, but the last step — setting accountEnabled correctly — turned out to be the source of the most serious bug in the whole project. It’s covered in detail in part 3.

UPN and email are not the same thing

One problem that showed up right away was that my Entra ID tenant only had its default domain verified, not a custom domain of its own. userPrincipalName (UPN) is the sign-in name a user actually logs in with in Entra ID, and it has to sit on a domain the tenant has verified ownership of.

The fix was to separate the two fields:

  • userPrincipalName is set to the tenant’s verified domain, since Entra ID requires that for sign-in.
  • mail keeps the user’s real, actual email address.

This is also how many companies solve it in practice: the sign-in name and the address colleagues actually email aren’t always identical strings, even though they often happen to look alike.

What this rests on

Provisioning to Entra ID rests on three things that tie together: a narrowly scoped app registration with only the permissions actually needed, an authentication flow (Client Credentials) built for programs rather than people, and a clear rule for how data maps between the HR system’s view of a person and Entra ID’s requirements for sign-in identities.

The next part in the series covers what happens when this isn’t enough — when a Graph call fails, an event gets dropped, or a bug sends the wrong status to Entra — and how reconciliation and the JML flow catch it.
