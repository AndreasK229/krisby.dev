One case: Emma loses FinanceApp access

The evidence and decisions behind the demo.

  1. 01

    Locate the failure

    Emma reports lost access. The scenario’s sign-in evidence points to an authorization failure. I check the account and app access before changing anything.

  2. 02

    Confirm the business need

    Her Finance role supports the request. Anna, the access owner, confirms normal FinanceApp access—not broader finance or admin privileges.

  3. 03

    Check the real assignment

    I inspect FinanceApp in the Entra portal and restore the approved user assignment. With the optional app mapping, I can read that assignment in the lab. The simulator’s app-access state is maintained separately.

  4. 04

    Verify and explain why

    A fresh scenario test checks access. I document the lifecycle cause and prevention step before closing. Real FinanceApp access needs its own test.

The scenario’s root cause: an HR cost-center change from FIN-OPS to FIN-SHARED triggers a lifecycle recalculation that removes the app assignment.

Prevention to investigate: review the Finance access rule and approval path before another source-data change removes required access.

Inside the implementation

What the app does itself

The backend creates the case, evaluates access and checks the closure rules. Persona wording is not the source of truth.

React interface→Fastify API→TypeScript services→Lab state and audit trail

Scenario engine → linked ticket
Activating a scenario changes a local employee’s state and creates a linked ticket with supporting sign-in or lifecycle evidence. The ticket keeps a link to that scenario.
Access engine → repeatable checks
Rules evaluate account, MFA, device, group and application state. A retry evaluates the current state and records a result; it is not an AI guess.
Persona engine → conversation
Employees answer from their lab context. Optional local Ollama adds generated replies, with scripted fallback. Access tests and closure remain rule-based.
Graph connector → external evidence
Read-only requests inspect tenant users and groups, map personas to users, and refresh linked account status. Only explicitly mapped apps get an assignment check, with a read timestamp and an unknown result if the read fails. It does not copy them into simulator access.

Emma’s closure checks

When is the ticket ready?

  • The target app assignment exists in the lab state.
  • The Finance role group remains and the account is enabled.
  • A successful fresh access test is recorded.
  • The root cause and governance decision are documented.

Missing requirements block closure. A later identity change invalidates the previous scenario verification. The selected root cause must match the expected scenario cause; the prevention note is recorded, not graded by AI.

These are scenario checks, not a tenant-wide compliance verdict. Tickets without a guided scenario can be closed manually.

No tenant setup is needed for simulation. Start with Emma and FinanceApp for an optional connected case. The connector does not create users, create apps or grant access.
